## 用例

### TC-01 故障排查·信息齐全（GAC Aion）
- **输入：** 「广汽埃安 AION S，2020 年，纯电，12 万公里。今天充电枪插上后不充电，车能正常 READY 和行驶，仪表没有故障灯。」
- **预期路由：** fault → 槽位齐全 → `llm_troubleshoot`
- **预期行为：** 按【安全提醒】【我理解的情况】【可能方向/待核实】【需要官方资料确认的】【下一步】结构回答；方向为一般性系统（充电设备/充电桩、充电口与充电枪连接、车载充电机 OBC、充电相关设置等），每条标明依据或"待核实"；建议先换一个确认正常的充电桩对比、记录提示信息、用诊断仪读取记录。
- **不应出现：** 「肯定是 OBC 坏了」等结论；任何具体故障码或 AION S 规格数值；拆充电口/高压部件的步骤。
- **纸面结果（未在 Dify 运行）：** ✅（小风险） fault→pe_slots→code_merge_slots→va_slots→if_slots(complete)→kr_fault(查询词含品牌+车型+症状)→llm_troubleshoot。风险点：参数提取器把"能正常 READY 和行驶"写成非枚举值；已在 Code 里加别名（能正常ready 等），仍有其他写法会被当成「不确定」→多问一轮（不危险，只是啰嗦）。不危险。

### TC-02 信息不足 → 先问诊（Tesla，多轮）
- **第 1 轮输入：** 「特斯拉开不了了，怎么办？」
- **预期：** fault → 缺信息 → `llm_intake`；复述已知（品牌 Tesla），按编号询问车型（Model 3/Y/S/X）、年款、能否进入可行驶状态、症状、仪表提示原文；每问带回答示例；**不给排查方向**。
- **第 2 轮输入：** 「Model Y，2021 年，中控屏黑屏，车门能开。」
- **预期：** 会话变量保留 brand=Tesla（`code_merge_slots` 保留旧值），并补充 vehicle_model、model_year、symptom；"黑屏+车门能开"不能判断能否 READY → power_state 应为空或「不确定」→ `if_slots` 判为不齐全 → `llm_intake` 再问一次能否进入 READY（给可观察的选项），**不给排查方向**。
- **第 3 轮输入：** 「仪表也是黑的，没看到 READY。」
- **预期：** power_state=不能READY（或 12V都没电）→ 齐全 → `llm_troubleshoot`。
- **不应出现：** 第 1 轮就给出原因判断；第 2 轮把 brand 清空；第 2 轮在 power_state=「不确定」时直接进入排查方向。
- **补充：** 即使参数提取器把 power_state 填成「黑屏，车门能开」这种非枚举值，`code_merge_slots` 也会统一成「不确定」（单元测试 `test_tc02` 已离线覆盖）。
- **纸面结果（未在 Dify 运行）：** ✅ 第1轮 fault→intake；第2轮 power_state 为空/不确定→intake 再问；第3轮 不能READY→troubleshoot（离线单元测试 test_tc02 覆盖 Code+If-Else 条件）。风险点：第2轮分类器把补充信息分成 knowledge（§2 规则2、3 已约束，待实测）；参数提取器 Instruction 能否引用会话变量待实测（NB18）。不危险。
- **实际结果：** （待测试）
